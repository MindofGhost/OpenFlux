# OpenFlux

[English](README.md) | **Русский**

Исследовательский инструмент сетевого стека. TCP-туннель с подключаемыми транспортами.

## Обзор
```
Client (SOCKS5) --> Transport --> Exit Node --> Internet
```

## Требования
1. Golang v. 1.26.3+ — требуется для сборки бинарника десктопного клиента / выходной ноды (universal-bypass-tool);
2. Android Native Development Kit (NDK) v.27.0.12077973+ — требуется для сборки бинарника для Android-клиента;
3. XCode v. 26.6+ — требуется для сборки бинарника для iOS-клиента;
4. VPS / VDS выходная нода на Linux.

## Обзор

TCP-пакеты передаются через Transport. На данный момент доступны два транспорта:
1. Yandex — отправляет пакеты через курсорные сообщения Yandex Docs;
2. Max — отправляет пакеты через WebRTC DataChannel.

Клиентская часть запускает SOCKS5-прокси, выходная нода декапсулирует и пересылает пакеты в пункт назначения.

## Использование

### 1. Настройка выходной ноды
1. У вас должен быть root-доступ выходной ноде;
2. Поддерживается только устаревший редактор документов Yandex (переключается в настройках интерфейса).

Команды для настройки выходной ноды:
```bash
sudo iptables -A OUTPUT -p tcp --tcp-flags RST RST -j DROP
sudo ./universal-bypass-tool --exit-node --url "YOUR_YANDEX_DOC_URL" --debug
```

### 1. Настройка десктопного клиента:

Команды для настройки десктопного клиента:
```bash
./universal-bypass-tool --client --url "YOUR_YANDEX_DOC_URL" --socks5 :1080 --debug
```

Затем настройте SOCKS5-прокси в браузере на localhost:1080.

## TCP-транспорт через несколько документов

Соберите программу: `go build -o openflux .`.
В режиме `--mode tcp` можно повторить `--url`: сервер подключится ко всем
указанным документам, а каждый клиент может использовать один или несколько из них.

```bash
# Сервер: принимать соединения через документы A и B.
./openflux --mode tcp --server --transport yandex \
  --url "DOCUMENT_A_URL" --url "DOCUMENT_B_URL" --target 127.0.0.1:443

# Клиент: распределять новые TCP-соединения между A и B.
./openflux --mode tcp --client --transport yandex \
  --url "DOCUMENT_A_URL" --url "DOCUMENT_B_URL" --listen 127.0.0.1:15000

# Другой клиент: использовать только B.
./openflux --mode tcp --client --transport yandex \
  --url "DOCUMENT_B_URL" --listen 127.0.0.1:15000
```

AnyTLS/VLESS-клиент направляется на `127.0.0.1:15000` с сохранением SNI и проверки
сертификата настоящего сервера. Мост передаёт байты TCP и не завершает TLS.
Каждый документ должен быть подключён к одному экземпляру сервера моста.

На каждый документ открывается отдельная WebSocket-сессия. Новые TCP-соединения
поочерёдно распределяются между авторизованными сессиями; отключённые пропускаются.
Каждое соединение закреплено за одним документом, и ответ возвращается через него.
Порядок ссылок у клиента и сервера может различаться. Клиенты, подключённые только
к A, не получают сообщения документа B.

При обрыве документа закрываются только его TCP-соединения. Остальные продолжают
работать; после восстановления документ снова используется для новых соединений.
Переноса действующих соединений между документами и объединения их скорости
для одного TCP-потока нет. Авторизация в документе сама по себе не подтверждает
наличие сервера моста: при его отсутствии открытие TCP-потока завершится по тайм-ауту.

`--tcp-max-connections` (по умолчанию 1024) ограничивает весь пул в одном процессе.
`--tcp-timeout` (по умолчанию 30s) задаёт тайм-ауты TCP-моста.
`--tcp-window` задаёт число неподтверждённых блоков по 1024 байта на поток
в каждом направлении: по умолчанию 16 (16 КиБ), допустимо 1–256.
На клиенте и сервере задавайте одинаковое значение; по умолчанию это
`--tcp-window 16`. Увеличение окна увеличивает буферизацию и нагрузку на общую
очередь транспорта; выигрыш в скорости требуется измерить.

Для Яндекса попытки LZ4-сжатия отключены. Однобайтовый маркер несжатого сообщения
сохранён, как и возможность принимать LZ4-сообщения от прежних версий.
Для сравнения скорости обновите оба конца и задайте одинаковые окна.
В транспорте MAX сохранено прежнее сжатие.

В режиме Yandex TCP `--yandex-batch 6` объединяет до 6 сообщений в одно событие
курсора. Неполная пачка отправляется через 1 мс; размер пачки ограничен 64 КиБ
до Base64. Блоки остаются по 1 КиБ, окно остаётся 16 КиБ на поток.
ACK отправляется после обработки каждого входящего блока, без накопления
подтверждений и отдельного таймера ACK. Для отключения пакетирования используйте
`--yandex-batch 1`.

Для пакетирования обновите все стороны: прежние версии не понимают новый
формат пачки. Декодер новой версии принимает и одиночные сообщения.
Прежний режим SOCKS5/IP продолжает отправлять сообщения по одному.

Одинаковые ссылки исключаются из повторных подключений; разные ссылки на один
документ указывать не следует. Пул доступен для Yandex в режиме TCP;
прежний режим SOCKS5/IP использует один документ.

## Аренда документов и выбор сервера

Режим `--lease` доступен для Yandex TCP. Каждому серверу задаются его стартовые
документы через `--url` и отдельный пул для выдачи клиентам через `--lease-url`.
Документы создаются заранее. Пулы разных серверов не должны пересекаться;
разные ссылки на один документ также считаются пересечением.

Пример сервера A:

```bash
./universal-bypass-tool --mode tcp --server --transport yandex --lease \
  --target 127.0.0.1:443 \
  --url 'https://disk.yandex.ru/i/ENTRY_A' \
  --lease-url 'https://disk.yandex.ru/i/WORK_A1' \
  --lease-url 'https://disk.yandex.ru/i/WORK_A2' \
  --lease-state .openflux-state/server-a.json
```

Сервер B запускается со своими `ENTRY_B`, `WORK_B1`, `WORK_B2`, файлом состояния
и адресом целевого сервиса. Клиенту достаточно стартовых ссылок:

```bash
./universal-bypass-tool --mode tcp --client --transport yandex --lease \
  --listen 127.0.0.1:15000 \
  --url 'https://disk.yandex.ru/i/ENTRY_A' \
  --url 'https://disk.yandex.ru/i/ENTRY_B' \
  --lease-select least-clients \
  --lease-state .openflux-state/client.json
```

Замените ссылки в примерах своими. Для аренды принимаются HTTPS-ссылки
`disk.yandex.ru` и `disk.yandex.com`. AnyTLS/VLESS-сервис по-прежнему принимает
исходный TCP-поток; мост не завершает его TLS.

Клиент начинает передачу через доступные стартовые документы и параллельно
запрашивает предложения. `--lease-select first` выбирает первый ответ;
`least-clients` собирает ответы ещё 3 секунды после первого и выбирает сервер
с меньшим числом активных клиентов. При равенстве остаётся первый ответ.
Предложение ещё не резервирует документ: аренда фиксируется только у выбранного
сервера, поэтому остальные серверы не расходуют свой пул.

Новая ссылка проверяется отдельным ответом сервера на новом документе. После
этого клиент сохраняет аренду и направляет туда все новые TCP-соединения.
Старые остаются на прежних документах до завершения, но не дольше
`--lease-drain 30s`; затем оставшиеся TCP-соединения принудительно закрываются,
а клиент отключается от старых документов. Уже открытое TCP/TLS-соединение
не переносится между документами: приложению потребуется открыть новое.
Такой же порядок используется при смене ссылки во время продления.

Сервер сохраняет аренду до ответа клиенту. В течение `--lease-ttl 30m` документ
остаётся зарезервированным, даже если клиент отключился. Если все доступные
документы зарезервированы, сервер выбирает документ с наименьшим числом
арендаторов. При продлении общей аренды клиент переезжает на свободный документ,
если такой появился. Старая аренда сохраняется до своего срока, а при необходимости
продлевается на время переезда и повторных запросов.

Клиент продлевает аренду каждые `--lease-renew 5m` либо через половину оставшегося
срока, если она наступит раньше. При перезапуске действующая сохранённая ссылка
используется сразу. Если сервер на ней не отвечает за 15 секунд, клиент возвращается
к стартовым ссылкам. Истёкшая аренда также приводит к новому выбору сервера.
Управляющие запросы повторяются при потере; повторная выдача действующей
исключительной аренды сохраняет документ и токен.

Активность клиента определяется служебным сообщением раз в 30 секунд; через
90 секунд без сообщений он перестаёт учитываться в нагрузке. Это приблизительная
оценка, включающая клиентов на стартовых документах, а не число TCP-потоков.
После перезапуска сервера оценка восстанавливается по следующим сообщениям.
Отсутствие активности не отменяет сохранённую аренду.

В файле клиента автоматически сохраняется случайный постоянный идентификатор:
ручной `client-id` не нужен. Используйте отдельный файл для каждого устройства
и не копируйте клиентское состояние между устройствами. Файлы записываются
атомарно; второй процесс с тем же файлом не запускается. Повреждённый файл
вызывает ошибку, а не сброс аренд. Сервер должен сохранять свой файл при перезапуске.
Аренда распределяет нагрузку, но не делает общий документ приватным и не заменяет
аутентификацию целевого сервиса.

Сервер держит по одной сессии на каждый стартовый и выдаваемый документ, включая
свободные. После переезда клиент обычно держит одну сессию; во время выбора и
завершения старых потоков сессий временно больше. Без `--lease` сохраняется обычная
работа статического пула. Батчи остаются по 6, окно — 16 КиБ на поток.

| Флаг аренды | По умолчанию | Назначение |
|---|---|---|
| `--lease` | `false` | Включить механизм аренды на клиенте и сервере |
| `--lease-url` | — | Документ серверного пула, флаг можно повторять |
| `--lease-state` | — | Обязательный путь к файлу состояния |
| `--lease-select` | `first` | Выбор клиента: `first` или `least-clients` |
| `--lease-ttl` | `30m` | Срок аренды, задаётся сервером |
| `--lease-renew` | `5m` | Интервал продления на клиенте |
| `--lease-drain` | `30s` | Время завершения старых TCP-потоков на клиенте; на сервере участвует в сохранении старой аренды |
| `--lease-discovery` | `3s` | Сбор предложений для `least-clients`, меньше 15s |

Вы можете реализовать интерфейс `Transport` из `transport/transport.go` и зарегистрировать свой транспорт в switch-блоке в main.go.
